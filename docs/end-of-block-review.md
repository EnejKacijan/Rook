# End-of-Block Review → Next Block

Implementation and verification report — 6 September 2026. No commit or push.

## 1–3. Completion architecture and entry points

1. Existing Training Blocks use stable block/week/workout identities, a logical `currentWeek` cursor, and workout snapshots. Week prescriptions already adjust reps, effort, main-set volume and deload targets. The old follow-up UI copied a plan without a retrospective or guarded persistence.
2. A week resolves only when every required logical workout has a completed session record or an explicit resolved skip. Calendar expiry does not advance it. The final carried workout remains an obligation of its original block/week. Optional sessions do not satisfy or block required obligations. An active workout from the block blocks advancement. Existing early-finish resolution is preserved, but zero logged work is not called completed training in the review. Pending skips remain reversible Flexible Week state; only skips which resolve a week are archived. Existing migrated week cursors are respected, not retrospectively rewritten.
3. Today’s existing `REVIEW BLOCK` entry opens the review, including on a rest day. The existing Training Block sheet also opens it and exposes prior archived block summaries. No global tab or navigation redesign.

## 4–10. Evidence and metrics

4. Summary: actual/planned sessions, logged/accepted prescribed working sets, moved/skipped sessions, early-finish explanation, optional completed sessions, deload context, progressed/held/review counts and quiet PR highlights. Exercise outcomes expose comparable-session counts, load/repetition evidence and eligible estimated 1RM.
5. Completed records are deduplicated by logical block-workout identity (optional sessions by optional ID); superseded records are excluded. A session with logged work contributes once. Zero-log early finish does not inflate completed training. Accepted recorded set prescriptions form the working-set denominator; warm-ups and added sets are not required working sets. PR highlights count each exercise/session once, not each PR type. Outcome counts describe programmed exercise entries; the same canonical exercise in two program slots has separate prescription-specific evidence.
6. Outcomes are `Progressed`, `Held`, `Review`, or `Insufficient data`. Held is neutral. Review does not automatically replace an exercise.
7. At least two complete comparable exposures are needed for a progression recommendation. Comparison requires the same program slot, canonical exercise, rep range, target RIR, logging mode and planned set count. Standard progression-compatible sets only. Existing progression thresholds decide load recommendations and repeated underperformance/stall. One bad exposure is not sufficient.
8. The existing `progressionFor` engine supplies loads; no new progression formula. Actual load/rep improvement can also explain a progressed outcome. Existing Performance Insights supplies Epley estimates for eligible sets in its 1–12 rep range. UI explicitly says estimated, not measured; no speculative RIR adjustment.
9. Moved sessions count once and remain factual movement, not failed adherence. Skipped sessions are separate, including final skips without invented History records. Accepted Adjust Today sets are the denominator; adjusted sessions and temporary equipment adaptations are excluded from comparable progression/replacement evidence. A completed slot is not also counted as skipped.
10. Deload sessions contribute actual completed work but are excluded from negative/comparable progression evidence. The summary says deload was recorded, not that reduced targets imply regression.

## 11–18. Proposal and user control

11. Proposals are ephemeral, deterministic and entirely local. Default: retain the program, week definitions, duration and deload. Only existing-engine load increases or evidence-supported replacement suggestions appear as changes.
12. Progressing: keep and review supported load progression. Held: keep. Insufficient: keep. Review/stall: keep unless repeated substitution evidence supports an explicit alternative. No automatic escalation.
13. A replacement needs at least four non-deload/non-adjusted recorded appearances, at least three substitutions to that candidate and at least 60% frequency. Permanent plan edits are not treated as temporary substitution evidence. Strict shared intent/equipment/restriction ranking gates all choices. Defaults to **Keep current**. Replacement loads are reset and subsequently use only that exercise’s own history.
14. No new block-to-block set-volume, rep-range or RIR escalation was justified by existing structured rules. Base prescriptions and existing within-block progression are preserved; no no-op diffs or arbitrary rotation. Restarting Week 1 intentionally restores the existing base-week effort pattern after a deload/peak.
15. Same block length, deload position and week definitions; new stable identities for block, weeks and obligations. Start date is the next scheduled day, avoiding a second programmed session on an already-trained day.
16. Each proposed load can be kept or accepted. Each proposed replacement can be kept, accepted, or changed through compatible search. Native radios expose selected state. Unchanged prescriptions remain inspectable. Plate-infeasible loads display existing calculator alternatives without silently rounding the target.
17. Secondary `REPEAT BLOCK` still requires review and explicit Start; it retains structure with new identity and no duplicated workouts.
18. `NOT NOW`, Cancel and normal dismissal do not alter the plan, create a version or automatically reopen the review.

## 19–25. Integration and durability

19. Explicit successful apply creates exactly one `Next block` Plan History version. Opening/reviewing/cancelling creates none. Existing parent/snapshot/retention behavior is reused.
20. Flexible Week records carry block identity. Sequence-resolving skips feed the block ledger; unfinished final carry-forward prevents premature completion. On approved transition, unstarted temporary schedules/overrides/Adjust Today state are cleared, as stated in review. Completed snapshots remain fixed.
21. Permanent choices use the default/base Gym Profile, not a temporary hotel environment. Smart Substitutions remains authoritative. Custom candidates with sufficient taxonomy pass the same strict gate separately from the built-in loadable shortlist; unknown intent is never invented. No global substitution rules changed.
22. History and Progress continue deriving from unchanged authoritative workout records. Approved starting loads have a block-scoped first-exposure marker so old-history initialization cannot overwrite the reviewed choice; later exposures return to normal progression. Coach context distinguishes completed-review-available from new-block Week 1. Existing Progress layout and weekly calculations are unchanged.
23. Fingerprints include permanent plan/block, workout/correction evidence, active state, temporary schedules, profile, gym/custom/preference inputs and version identities. Apply regenerates the proposal/date and rejects changes. Active workouts block apply. The error and Review Again action remain visible next to the disabled CTA.
24. Apply constructs a cloned candidate including archive, new block and Plan Version, then invokes existing whole-state persistence. Only successful persistence publishes React state; a false return or thrown storage error leaves the original state intact. The UI success lock and stale source identity prevent duplicate apply. Existing storage/restore recovery remains in place; no claim of a new multi-store database transaction.
25. Existing backup serialization includes block snapshots, archived program/review summaries, resolved skips and approved load markers. Added validation rejects malformed review counts/rows, archived program shape and broken resolved-skip references. ZIP round-trip tests cover pending review, applied next block and accepted custom replacement; real browser clean-profile restore covers pending/applied states. Ephemeral choices are intentionally regenerated after reload, not backed up. Existing 24-block archive retention remains unchanged; full source workout history is not deleted by it. Archived summaries are frozen at transition and do not mutate when later blocks begin.

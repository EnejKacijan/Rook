# ROOK Account & Sync — implementation boundary

Status: local app implementation for review. Firebase client, anonymous authentication, Google popup linking, per-entity Firestore adapter, durable sidecar, coordinator, UI, and owner-only rules exist in the working tree. The public Web app config is present only in the ignored local `.env`. On 2026-09-28 the owner-only Firestore rules were deployed to `rook-1d2c8` without deploying the web app. The released ruleset matches the local file; Anonymous and Google Auth are enabled, and the Netlify domain is authorized. Isolated real-service tests confirmed anonymous backup, protected recovery, access isolation, offline/reconnect, and tombstones. Actual Google linking and physical-iPhone recovery are still rollout gates.

## Authority and identity

The existing `profile.id` remains the training-data lineage ID. Firebase Auth UID, if Firebase is selected, is an account access identity and never replaces profile, workout, exercise-instance, occurrence, or set IDs. A device/install ID distinguishes mutation authors, not users. For an empty local install with Firebase configured, Auth initialization and the current UID's cloud lookup finish before first-run UI can mount. Auth `null`, timeout, or error cannot imply a blank ROOK profile. An established local profile opens without waiting for cloud availability.

`localStateStorage` remains the only durable writer. Its verified primary write, generation receipt, continuity guard, recovery checkpoint, restore journal, and explicit deletion semantics remain authoritative. Cloud work starts only after a successful local write and validated hydration. An empty install with a persisted anonymous or linked UID can restore that UID's populated cloud profile before the domain app mounts. A new device without a persisted account requires explicit Google sign-in. Both routes validate local emptiness, cloud lineage and entities, and the resulting local write before publishing recovered state. A normal cloud read never directly renders a new root state.

## Cloud layout and revisions

The Firestore account anchor is `/rookAccounts/{auth.uid}` with `syncSchemaVersion`, the immutable `profileId` lineage, and `createdAt`. Each entity is `/rookAccounts/{auth.uid}/entities/{sha256(domain + ':' + JSON.stringify(entityId))}`. The document holds `syncSchemaVersion`, `profileId`, `domain`, `entityId`, `ordinal`, `revision`, `lastMutationId`, `updatedAt`, `deleted`, `digest`, and `value`. `entityId` is `root` for a singleton and its stable ID for a collection item. `ordinal` is null for a singleton and the original array index for a collection item; it is part of the item digest so recovery preserves list order even when Firestore returns documents in another order. The adapter verifies that each read document ID matches the digest of its declared domain and entity ID. Firestore Security Rules constrain account ownership to the authenticated path UID; they do not replace adapter-side identity and digest validation.

Use per-account, per-domain documents, not a whole-root document. Initial scope: profile/settings, program and plan versions, schedule/overrides, gym profiles and restrictions, active workout, completed workouts, optional sessions, templates, custom exercises, and recorded working-weight/check-in data. Core records with stable IDs (especially workouts, templates, custom exercises) are separate documents. Coach conversations and workout-photo blobs remain local in the first release. A workout's local photo reference must not imply that its blob was synced; recovered devices show it as unavailable or omit the local-only reference.

Each cloud entity has `{syncSchemaVersion, profileId, domain, entityId, ordinal, revision, lastMutationId, updatedAt, deleted, digest, value}`. Values are projected through the same JSON serialization used for the durable local root before digesting or sending them to Firestore; this removes optional nested `undefined` properties that Firestore rejects without changing the saved local object. The digest sorts object keys recursively because Firestore does not preserve JavaScript property insertion order; array order and item ordinal remain significant. Revision is a server-transaction-controlled monotonically increasing integer. `updatedAt` is diagnostic only. An upsert or tombstone mutation has a stable digest-based mutation ID, base revision, local generation, account/profile identity, and payload digest. A retry of the same mutation ID is a no-op; a different mutation with an outdated base revision is a conflict. Cloud rules restrict paths to `request.auth.uid` and disallow clients changing ownership or bypassing revision checks. Schema versions newer than the client halt writes.

Local mutation intent needs a durable outbox associated with the committed root generation. A separate best-effort key written after `localStorage` is **not sufficient** as the sole source of pending values. The implementation keeps the verified primary root authoritative and regenerates per-entity pending mutations by comparing it with the sidecar's last acknowledged revisions on every scan. Explicit deletion intents are written only after the corresponding local deletion succeeds. If an intent cannot be persisted, cloud deletion is blocked for review; absence alone never deletes a cloud record. UI says “Synced” only after a remote acknowledgement for every pending mutation.

Tombstones currently remain indefinitely. A weeks-old device cannot resurrect a deleted workout because it must reconcile against the tombstone's revision before upload. Missing cloud documents are never interpreted as deletes. The retention/compaction policy still needs a separately reviewed design before any physical deletion of tombstones.

## First sync and conflicts

Hydrate and validate local data, create and verify a last-known-good checkpoint before cloud mutation, authenticate, read the cloud account anchor and entities, then classify. Local populated/cloud empty uploads local entities. Local empty/cloud populated restores after verifying ownership of the persisted UID or explicit Google sign-in. Same-lineage non-conflicting entities reconcile by revision. Different lineage, simultaneous changes to one entity, or different active workouts stop in a needs-attention state; neither side is overwritten. Same-session concurrent edits also stop rather than attempting an unproven merge. A completed workout uses its stable ID so retry cannot duplicate history.

First-run UI is authorized by one startup decision boundary. A corrupt local root or recoverable checkpoint stays in the existing local recovery screen. If the primary is missing and no checkpoint bytes exist, a verified persisted account with a complete cloud profile can offer an explicit cloud restore; the user action uses the guarded P0 replacement writer and verifies the result. If that missing-primary case has no persisted credential, the local recovery screen offers Google sign-in and then retries the account check without deleting local evidence. For an empty local profile with Firebase configured, Auth and a bounded server read must both succeed. Empty cloud plus a newly created anonymous UID can start setup; an older anonymous UID with empty cloud requires an explicit fresh-start choice. Any populated, malformed, unsupported, or conflicting cloud result blocks onboarding and preserves local bytes. The startup result is checked against current local raw value, generation, and Auth UID after async work. Sync downloads also recheck the Auth UID before writing locally.

If both the local profile and the old anonymous credential are lost, ROOK cannot prove ownership of the old anonymous cloud account and cannot discover it by name or device metadata. A newly created anonymous UID with empty cloud can start over. Securing the account with Google is required for recovery after losing the anonymous credential.

An existing-account link collision is **not** an implicit sign-in or merge. The anonymous UID and local data remain, and automatic linking stops for review. Successful Google linking keeps the same UID and profile ID. Sign out preserves A's local training data behind a lock; signing in with B while A is stored here is rejected rather than showing A's data or silently merging. Full multi-account namespaces and account deletion are not implemented in this pass. “Remove data from this device” remains a separate explicit local action and does not delete the cloud account.

## Operational gates

The runtime client only initializes when a complete `VITE_ROOK_FIREBASE_*` Web config is present. Auth provider/domain setup and Firestore rules deployment are complete. Production web enablement remains blocked until a real Google link, two-device Google recovery, and physical-iPhone tests pass. A disabled or unconfigured feature must not show a backup-success claim. Existing local backups remain available throughout.

Privacy-safe diagnostics: account status category, sync schema/revision, pending count, last acknowledged backup time, and error category; never exercise content, notes, Coach messages, photo bytes, tokens, or raw provider errors.
